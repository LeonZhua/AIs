# DeepSeek Round 1 Review

## 核心判断
方案试图用多 AI 协同评审来保障多 AI 执行方案的可行性与安全性，但当前设计在安全边界、执行闭环、失败降级和过度设计四个维度上存在多个致命缺陷。如果直接实施，既不能证明评审结果能安全落地，也无法防御评审过程自身造成的敏感信息外泄，整体处于“纸上多 AI”状态，缺乏可实施的工程骨架。

## P0/P1 风险

### P0 风险：评审阶段敏感数据外泄，安全边界缺失
- **问题**：默认不执行本地操作（dry-run），但“多 AI 评审”必然需要将待评审的方案、代码、配置、甚至可能包含生产参数的任务描述发送给外部模型（通过 API）。当前设计没有定义输入数据的敏感度分级与脱敏策略，仅在输出端做脱敏扫描。这意味着任何被评审的目标方案都可能连同密钥、内部架构、数据库模式等一并泄露给第三方模型供应商。
- **影响**：直接违背组织安全策略，可能造成密钥、业务逻辑、隐私数据泄露。
- **必须修复**：在评审入口增加“评审窗口输入清洗与脱敏”门禁，评审输入不得包含任何生产密钥、连接串、客户数据；敏感关键词必须替换或掩码后发送；如果无法脱敏，则任务不得进入多 AI 评审管道。

### P0 风险：多 AI 执行方案可行性无法闭环验证
- **问题**：方案目标为“确保多 AI 执行方案可行”，但整个流程仅覆盖评审和验收，中间“实现/落地”是一个黑盒。没有定义谁负责执行、执行环境如何隔离、执行过程的监控与回滚机制。评审通过的 final-plan 可能包含 AI 无法执行或执行时产生不可控副作用的步骤，验收阶段仅是对静态产物的二次评审，无法验证真实执行行为。
- **影响**：评审结论与实际执行完全脱钩，系统可能放行无法执行的计划，导致资源浪费或安全事故。
- **必须修复**：必须在流程中显式定义执行主体（人工或限定沙箱内的 AI Agent）及执行状态收集机制，验收阶段必须比对“期待行为”与“实际执行痕迹”，否则本系统的存在意义不成立。

### P1 风险：任务拆分门禁无人工确认与集成校验
- **问题**：Codex 决定任务过大并进行拆解，但没有定义“过大”的量化阈值，也未引入人工确认。拆分后的子任务要求“可独立评审、实现、验收”，但未检查子任务间的依赖关系和集成顺序。一旦拆分不当，后续并行评审会忽视全局约束，最终集成时出现接口不匹配、状态冲突等严重问题。
- **影响**：拆分策略错误会导致整体方案失败，而评审环节无法发现，直至集成阶段崩溃。
- **修复建议**：拆分后必须生成 task-breakdown.md 并阻塞流程，由人类确认子任务边界、依赖关系和集成测试策略；子任务之间增加“集成契约” artifact，供后续评审交叉校验。

### P1 风险：验收阶段无 rework 闭环
- **问题**：多 AI 验收生成 acceptance-report 和 rework-items，但未定义 rework 后的再验证流程。开发者根据 rework-items 修改后，是否自动重新触发验收？若无，则验收仅是一次性检查，无法保证修复质量。
- **影响**：可能导致未完全修复的缺陷进入后续阶段，验收失效。
- **修复建议**：必须设定 rework 循环上限与重新验收的触发条件；明确 rework 后至少要经过 Codex + DeepSeek 的安全复验。

### P1 风险：失败降级策略过于模糊
- **问题**：任何 AI 输出失败、超时、空输出或解析失败时，“进入人工确认/降级”，但降级的具体路径（暂停流程、跳过该审查、使用默认安全假设、切换备用评审器）未定义。这种模糊性将导致操作人员每次遇到故障都要临时决策，增加误判概率。
- **影响**：系统在异常路径上行为不可预测，可能被错误地放行或长时间阻塞。
- **修复建议**：定义明确的降级矩阵：例如 DeepSeek 超时则任务进入待审核队列，标记为“无 AI 反方检查”；Qwen 解析失败则强制人工替换；连续失败三次则任务终止并通知责任人。

## P2/P3 风险

### P2 风险：静态规则触发人工确认后缺少操作协议
- **问题**：本地静态风险规则默认触发人工确认，但没有规定人工确认的形式（Jira 审批、CI 门禁、即时 IM 通知）、时效和处理人角色。可能造成关键决策被忽略或延迟。
- **影响**：高风险项可能因确认流程不明确而被搁置或误操作。
- **修复建议**：为静态风险项绑定确认渠道和 SLA，所有确认记录写入 human-decisions.md，并附加签名。

### P2 风险：Artifact 审计无法防篡改和追溯
- **问题**：方案列举了大量 artifact，但缺少完整性校验（如哈希链、签名）。若流程中任一中间产物被人或 AI 修改，验收报告可能基于虚假证据生成。
- **影响**：审计追溯不可信，定位问题时无法确定是哪一环节被篡改。
- **修复建议**：对每份 artifact 生成摘要并存放在不可变记录中；在裁决和验收时验证前置 artifact 摘要的一致性。

### P2 风险：成本记录但不阻止失控调用
- **问题**：token/cost 只记录不设硬上限，无法防止因 prompt 膨胀或逻辑死循环导致的费用爆炸。
- **影响**：财务不可控，可能产生高额账单。
- **修复建议**：增加软熔断机制，当单任务或单日成本超过阈值时发出告警并暂停自动评审，等待人工确认后继续。

### P3 风险：三模型协同存在过度设计嫌疑
- **问题**：使用 Qwen（结构化方案）、DeepSeek（反方风险）、Codex（裁决）三种模型，交互复杂，调试和维护成本极高。是否可以用 Codex + 规则引擎 + 单一外部模型（如 DeepSeek 兼顾方案审查与风险扫描）替代？当前方案未论证多模型的不可替代性。
- **影响**：增加系统延迟、成本和故障点，而对结果的增益未经证实。
- **建议**：提供方案简化实验或对照：单模型 + 规则扫描是否已经能达到相近的安全与质量水平；如果多模型有显著提升，请提供量化证据，否则建议在第一版中使用最小化架构。

## 必须保留的人工确认
- **拆分门禁**：任何自动任务拆分必须由熟悉业务的人类确认子任务边界和集成契约。
- **所有静态规则触发的高风险项**：生产配置、数据库、权限、资金、密钥轮换、隐私数据等评审结论，不得自动通过，必须有人工签字。
- **外部 API 调用的敏感输入**：任何包含疑似敏感信息（通过关键词扫描）的任务进入评审前必须人工确认已脱敏。
- **验收 report 中的高危 rework 项关闭**：涉及安全边界或资金逻辑的 rework，修复后必须人工确认才能关闭。
- **系统首次启用或规则更新后的首次执行**：必须人工监督全流程，确认无误后方可自动化。

## 建议最终方案要点
1. **增加评审输入安全网**：在 Codex 生成 seed package 后立即执行脱敏扫描，拒绝含明文密钥、PII 的任务进入后续 AI 流。
2. **补齐执行与验收闭环**：明确定义执行环境（例如沙箱 Agent），将执行日志和状态纳入证据收集，验收时进行预期与实际差异分析，而非仅静态文档评审。
3. **注入确定性降级路径**：用决策表定义所有异常场景的处理动作，避免自由裁量。
4. **强化 artifact 完整性**：所有产物纳入内容寻址存储，裁决和验收时校验输入哈希链。
5. **评估架构简化**：先实现“Codex 裁决 + DeepSeek 反方 + 规则引擎”的简化版，验证有效性后再考虑引入 Qwen 等其他模型。
6. **增加 dry-run 确切定义**：dry-run 应指“不调用外部模型，仅用本地规则和缓存的历史评审模板”；如果必须调用外部模型，则必须在方案中明确并经过安全审批。
