# Qwen Round 1 Review

## 核心判断
方案具备较好的安全基线与工程化意识（双开关控制、环境变量隔离、脱敏扫描、静态风险规则、调用日志记录），整体方向符合“AI 辅助工程化”的演进趋势。但当前设计**偏向静态文本流转，缺乏运行时验证、状态机闭环与强类型契约**。多 AI 评审无法直接保证多 AI 执行可行性；任务拆分缺乏依赖治理；验收阶段未形成自动化回流；产物格式过度依赖 Markdown，不利于机器解析与门禁自动化。整体存在一定过度设计倾向，需收敛核心链路、强化 Schema-First 与反馈回路后方可进入实施阶段。

## 主要问题
| 优先级 | 问题域 | 具体描述 |
|:---:|:---|:---|
| **P0** | 验收闭环断裂 | 步骤 10 产出 `rework-items.md` 后流程终止，未定义回流至 `task-breakdown` 或 `final-plan` 的触发条件与状态机，导致“评审-实现-验收”为开环，无法自动驱动修复与重验。 |
| **P0** | 静态评审无法保证执行可行性 | 多 AI 评审仅针对文本方案进行逻辑/风险推演，未覆盖运行时依赖、网络连通性、权限生效、环境版本等动态因素。直接执行存在高概率运行时失败风险。 |
| **P1** | 任务拆分机制缺乏依赖与合并策略 | 步骤 2 仅凭“任务过大”触发拆分，未定义复杂度度量标准（如 Token/圈复杂度/依赖节点数）；未声明子任务间的 DAG 依赖关系；未定义子任务产物的合并规则与冲突解决机制。 |
| **P1** | 产物格式不利于自动化门禁 | 14 个 artifact 中 11 个为 `.md`。Markdown 缺乏强类型约束，难以被解析器稳定提取决策字段（如 `approved: true/false`、`risk_level`、`rework_scope`），易导致门禁逻辑脆弱。 |
| **P1** | 成本/Token 无熔断机制 | 步骤 8 明确“不设置硬上限，不因成本阈值阻断”。在多 AI 并发或死循环重试场景下，极易引发配额耗尽、账单失控或下游服务雪崩。 |
| **P2** | API 编排缺乏容错与并发控制 | 未定义多 AI 调用的执行模式（串行/并行）、超时策略、指数退避重试、限流降级。若某模型响应慢或返回非结构化内容，将阻塞整个评审流水线。 |
| **P2** | 审计日志缺乏关联追踪与防篡改 | `calls-log.jsonl` 仅记录调用，未要求全局 `trace_id` 串联 seed→breakdown→review→adjudication→acceptance 全链路；未说明日志的集中存储、哈希校验或防篡改策略，合规审计能力不足。 |
| **P3** | 角色分工可能冗余 | 单任务引入 Qwen（编排）+ DeepSeek（反方）+ Codex（裁决）三模型，延迟与成本较高。若裁决逻辑可由确定性规则+单模型输出覆盖，存在过度设计风险。 |

## 必须修改
1. **建立验收回流状态机**：将 `rework-items` 明确映射为状态机事件。若存在 `rework-items`，自动触发 `plan-revision` 或 `sub-task-retry` 分支，并限制最大回流次数（如 `max_rework_cycles=3`），超限则强制转人工。
2. **增加 Pre-flight / 沙箱预检阶段**：在 `final-plan` 通过后、真实执行前，插入轻量级预检（依赖解析、权限模拟、网络连通性探测、配置语法校验）。预检失败直接拦截，不进入多 AI 执行。
3. **核心产物强制 JSON Schema 化**：将 `seed-package`、`task-breakdown`、`final-plan`、`adjudication`、`acceptance-report` 转为严格 JSON Schema。Markdown 仅作为人类可读附件（如 `*.md` 由 JSON 渲染生成）。门禁逻辑必须基于 JSON 字段解析。
4. **任务拆分引入 DAG 与合并契约**：`task-breakdown` 必须包含 `dependencies`、`execution_order`、`merge_strategy`（如 append/overwrite/conflict-resolve）。拆分后需经一次轻量级评审确认依赖图无环。
5. **增加成本/Token 软熔断与降级策略**：设置 `soft_cost_limit` 与 `max_retry_budget`。触发阈值时不直接阻断，而是降级为“仅本地静态检查+人工确认”或“跳过非关键 AI 评审”，并记录降级原因。

## 可接受风险
- **三模型并行评审的延迟与成本**：在 MVP 阶段可接受，后续可通过异步消息队列、结果缓存（相同输入复用评审结果）、模型路由（按任务复杂度动态选择单/双模型）优化。
- **静态风险规则覆盖不全**：当前依赖人工门禁兜底是可接受的过渡方案。需建立规则库版本化机制，按季度迭代补充生产配置、资金、隐私等场景。
- **审计日志暂不接不可变存储**：初期采用集中式结构化日志+定期快照即可满足内部追溯。若涉及金融/医疗合规，再引入 WORM 存储或链上哈希锚定。

## 建议最终方案要点
1. **架构收敛为状态机驱动**：采用明确的工作流引擎（如 Temporal / LangGraph / 自研 DAG 调度器）管理 `Seed → Breakdown → Review → Adjudication → Pre-flight → Execute → Acceptance → Rework/Close` 全生命周期，避免隐式流程跳跃。
2. **Schema-First 与契约测试**：所有 AI 输出必须通过 JSON Schema 校验，失败直接走降级/人工分支。为每个 artifact 定义版本号与字段必填/选填规则，配套自动化契约测试。
3. **闭环反馈与可观测性**：全链路注入 `trace_id`，日志结构化输出至集中平台。验收报告必须包含 `pass/fail`、`evidence_refs`、`rework_scope`、`next_action` 四要素，驱动状态机自动流转。
4. **安全与门禁分层**：
   - L0：环境变量隔离、脱敏扫描、双开关（`MULTI_REVIEW_API_CALLS` + `--execute`）
   - L1：静态规则拦截（DB/权限/资金/PII）→ 强制人工审批
   - L2：Pre-flight 动态预检 → 失败拦截
   - L3：成本/重试熔断 → 降级执行
5. **实施路径建议**：
   - **Phase 1 (MVP)**：单模型评审 + 强 Schema 校验 + 人工审批门禁 + 基础日志。跑通闭环。
   - **Phase 2**：引入多 AI 对抗评审 + DAG 任务拆分 + Pre-flight 预检 + 软熔断。
   - **Phase 3**：自动化回流状态机 + 审计防篡改 + 成本优化与模型路由。

> 注：本评审严格基于架构可实施性、工程化规范与安全边界展开。未涉及任何真实凭证、密钥或授权头信息。建议按 P0/P1 项完成改造后再进入代码实现与集成测试阶段。
