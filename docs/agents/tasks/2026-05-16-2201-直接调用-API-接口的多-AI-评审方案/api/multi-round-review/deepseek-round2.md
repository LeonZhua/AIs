# DeepSeek Round 2 Convergence

## 对 Qwen 意见的采纳/反驳

**总体意见：Qwen 第 1 轮审查精准识别了当前方案的核心断裂点，尤其是验收闭环、静态评审可行性和产物格式的工程化缺陷。我们整体接受 Qwen 提出的 P0/P1 问题，并同意其「状态机驱动 + Schema-First + 反馈回路」的收敛方向。但对部分具体建议，我们根据安全优先原则提出轻微修正或强化。以下是逐项立场：**

| 项目 | 立场 | 理由与修正 |
|---|---|---|
| P0 验收闭环断裂 | **完全采纳** | 必须构建 rework‑to‑replan 的自动回流机制，否则系统不可闭合。我们额外要求回流触发前必须对 rework 项做一次人工威胁分级，高危项强制人工关闭，防止自动循环绕过安全审批。 |
| P0 静态评审无法保证执行可行性 | **完全采纳** | 在 final‑plan 与真实执行之间必须插入 Pre‑flight 预检。我们进一步要求 Pre‑flight 必须在与执行环境隔离的沙箱内完成，且预检日志本身纳入证据链。 |
| P1 任务拆分缺乏依赖与合并策略 | **完全采纳** | task‑breakdown 必须显式包含 DAG、执行顺序与合并契约。我们额外要求拆分结果必须经过一次缩短版安全评审（至少 DeepSeek 反方审查），防止拆分改变全局安全属性。 |
| P1 产物格式不利于自动化门禁 | **完全采纳** | 核心产物必须 JSON Schema 化，Markdown 仅作人类可读副本。我们建议所有门禁判断基于 JSON 字段，并且门禁脚本本身经过签名存储。 |
| P1 成本/Token 无熔断机制 | **修正后采纳** | Qwen 建议设置软熔断阈值。我们同意，但必须明确定义：软熔断触发后不阻断当前安全关键评审，仅阻止后续新一轮自动化任务，并立即发出人工告警。熔断阈值需可配置且默认为保守值（如单任务 $5、单日 $50）。 |
| P2 API 编排容错与并发控制 | **完全采纳** | 引入指数退避、超时和并发度限制，所有非 2xx 或解析失败均转入明确的降级路径，不得静默跳过。 |
| P2 审计日志缺乏关联追踪与防篡改 | **完全采纳** | 全链路注入 trace_id，关键 artifact 附带内容哈希并存放在只追加日志中。初期可使用 Git‑like 内容寻址存储，后续再升级到 WORM。 |
| P3 角色分工可能冗余 | **部分采纳** | 在当前安全敏感场景下，使用 Qwen 负责结构化方案、DeepSeek 反方风险、Codex 本地裁决的三方架构，可提供“独立方案审查 + 对抗性风险发现 + 可审计裁决”的特质，暂时保留。但应在 Phase 2 后期根据数据决定是否可裁剪为 “Codex 裁决 + DeepSeek 反方” 简化版。Qwen 提出的「单模型+规则」替换实验是合理的，我们要求在 MVP 后期进行回溯对比测试。 |

## 最终方案必须包含（收敛骨架）

以下要点构成可安全落地的最小可行骨架，已整合 Qwen 核心建议并补齐 DeepSeek 第 1 轮审查看出的安全鸿沟：

1. **安全输入清洗门禁**（P0 新增）  
   在 seed‑package 生成后、任何外部 AI 调用前，执行强制脱敏扫描。规则集包括但不限于：密钥模式、连接字符串、内网 IP/域名、PII 特征。未通过清洗的任务**不得进入多 AI 评审**，直接转人工处置。清洗结果写入 artifact `safety‑input‑sanitization.json`。

2. **Schema‑First 核心产物**  
   - `seed‑package.json`（含 goal, constraints, model‑roles, verdict‑rules）  
   - `task‑breakdown.json`（含 DAG, dependencies, execution_order, merge_strategy）  
   - `qwen‑output.json`、`deepseek‑review.json`（强类型，含风险等级、决策字段）  
   - `adjudication.json`（最终裁决、需人工项、签字要求）  
   - `final‑plan.json`（含执行步骤、前置条件、回滚操作）  
   - `acceptance‑report.json`（含 pass/fail、evidence_refs、rework_scope、next_action）  
   所有 JSON 必须通过预注册的 Schema 校验，失败则转入降级（重试一次后仍失败转人工）。

3. **状态机驱动闭环**  
   工作流状态：`Seed → Sanitize → (Task Split) → Review → Adjudication → Pre‑flight → Execute → Acceptance → [Rework | Close]`。  
   - 若 acceptance 产生 `rework_scope`，自动进入 `Plan‑Revision` 子状态，更新 `final‑plan` 后重新触发 Review 与 Pre‑flight（最多 3 次循环）。  
   - 每次 rework 循环必须伴随 DeepSeek 安全复验，高危项需要新的人工签字。  
   - 所有状态转换记录在 append‑only `workflow‑states.jsonl` 中。

4. **Pre‑flight 动态预检**  
   位于 `final‑plan` 通过后、执行前，自动执行：  
   - 语法/配置校验（例如 YAML/JSON 有效性、Terraform plan）  
   - 权限模拟（通过只读 API 探测所需权限是否具备）  
   - 网络连通性探测（对目标 endpoint 的 TCP/HTTPS 连通性，不发送敏感数据）  
   - 依赖解析（所需工具、库版本是否存在）  
   任一预检失败即阻断执行，生成 `preflight‑failure.json`，要求人工介入。

5. **执行与证据收集**  
   明确执行主体：限定在隔离沙箱内的 AI Agent 或人工执行。执行过程需产生结构化日志（`execution‑trace.jsonl`）。此日志与之前的预期行为（来自 `final‑plan`）共同输入验收阶段。

6. **验收阶段行为对齐**  
   验收不再只针对静态产物，而是比对 `final‑plan` 中的期待步骤与实际执行痕迹。DeepSeek 验收时需分析差异，生成可操作的 rework 项（含严重度）。验收报告必须包含明确的 `next_action`（通过/返工/终止）。

7. **稳固的降级矩阵**  
   定义以下场景的确定行为（节选关键情形）：
   - Qwen 输出解析失败 → 重试一次，仍失败则走“仅 DeepSeek 反方 + 静态规则”精简评审，人工确认后放行。
   - DeepSeek 超时 → 50% 时间内等待重试，超时后降级为“无反方检查”，任务标记为高风险，必须人工审批。
   - 成本熔断触发 → 停止自动新任务，已在管道中的任务改走“本地静态规则 + 人工确认”通道。
   - 脱敏扫描命中 → 立即隔离输入，通知安全负责人，不得尝试自动脱敏后继续。

8. **不可变审计与完整性**  
   所有 artifact 在生成时计算 SHA‑256，连同 trace_id 写入 `artifact‑chain.jsonl`。裁决和验收阶段必须验证前置 artifact 哈希链的连续性，任何不一致均中止流程并报警。

9. **人工门禁硬编码**  
   以下情况**永远不能自动通过**（与 Qwer 一致并补充）：
   - 拆分门禁：任务拆分结构需人工确认。
   - 静态规则触发的高风险项：生产配置、DB 变更、权限提升、资金操作、隐私数据。
   - 任何 rework 项关联到安全边界或资金逻辑的关闭。
   - 首次系统启动及规则库更新后的首次运行。

10. **双开关强化**  
    调用任何外部 AI API 必须同时满足：
    - 环境变量 `MULTI_REVIEW_API_CALLS=enabled`
    - 命令行参数 `--execute`
    否则系统仅运行本地静态分析和 dry‑run 模拟（dry‑run 定义为“不调用外部模型”，可复用缓存的历史评审模板）。开关状态写入日志。

## 人工确认清单建议

基于上述方案，最终系统应强制要求人工确认的节点清单：

1. **安全输入确认**：输入清洗阶段发现疑似敏感信息，必须由安全责任人确认已脱敏或拒绝任务。  
2. **任务拆分审批**：任何自动生成的 task‑breakdown（含 DAG）需开发/架构负责人确认边界与合并策略。  
3. **静态风险审批**：裁决阶段若命中生产配置、DB、权限、资金、密钥轮换、隐私数据规则，必须由具备审批权限的工程师或安全人员签字。  
4. **Pre‑flight 失败处置**：预检失败后，必须人工决定重试、修改计划还是终止。  
5. **无反方检查任务审批**：DeepSeek 降级时，任务转为“无反方检查”状态，必须人工确认后方可继续。  
6. **高危 Rework 关闭**：验收 rework 项若关联安全边界或资金逻辑，修复后必须人工验证并签字。  
7. **首次/规则变更监管**：系统首次部署或静态规则集有重大更新后，首次全流程运行需人工全程监督。

每项确认均在 `human‑decisions.json` 中记录决策者、时间戳和签名（GPG 签名或等效），不可篡改。

## 剩余风险（已收敛后仍存在的可接受风险）

| 风险 | 级别 | 说明与缓解 |
|---|---|---|
| 多模型推理的固有不确定性 | 中 | 即使有强 Schema，AI 仍可能输出语法正确但逻辑错误的评审。缓解：DeepSeek 反方检查可捕捉部分矛盾；人工抽检在 Phase 1 保持。长期通过反馈样本微调模型。 |
| 静态风险规则覆盖不全 | 中 | 规则库不会涵盖所有业务特有高危操作。缓解：人工审批作为兜底，规则库以季度周期迭代，并允许团队贡献自定义规则。 |
| 外部模型供应商的数据驻留风险 | 低 | 经过严格的输入脱敏后，传输到外部模型的仅包含抽象任务描述，无明文敏感数据，且多数供应商有企业级合规认证。但仍需法务确认。 |
| 成本熔断误触发可能延误关键任务 | 低 | 熔断仅停止自动新任务，当前管道中任务可继续执行，并提供人工绕过机制。阈值可动态调整。 |
| 执行环境的沙箱逃逸风险 | 低 | 执行主体限定了沙箱 Agent，但仍需常规的沙箱加固、最小权限、网络隔离等运维措施，不属于本方案覆盖范围。 |
| 复杂 DAG 拆分导致碎片化安全上下文 | 中 | 拆分后子任务的安全特性可能不同于整体。缓解：拆分后强制进行一次全局安全评审，并在集成阶段二次校验契约。 |
| 人工确认疲劳导致误许 | 低 | 系统将确认项最小化，并提供清晰的上下文信息。仍需要通过培训和文化建设弥补。 |

**结论：** 经过以上收敛，方案已具备安全可落地的工程骨架，可据此进入 Phase 1 开发（单模型 + 强 Schema + 人工门禁 + 基础日志），并在后续迭代中逐步引入多 AI 对抗、DAG 拆分和自动化回流。建议在代码实现前，先针对上述必选骨架（安全输入清洗、Schema、状态机、Pre‑flight、降级矩阵）进行一次架构预演，以确保无漏。
