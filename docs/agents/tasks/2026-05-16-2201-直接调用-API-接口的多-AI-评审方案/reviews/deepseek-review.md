# DeepSeek API Review

## 被评方案核心假设

### Codex 第一轮种子包
- 假设通过一份结构化的本地种子包（JSON）就能统一约束后续所有外部模型的输入和行为，避免散乱自然语言描述。
- 假设“任务一句话目标与非目标 + 硬约束 + 模型职责矩阵 + 最小上下文 + 裁决规则”足以覆盖多 AI 评审的边界，且外部模型能严格据此输出。
- 假设 Qwen 负责方案编排、DeepSeek 负责反方风险，Codex 不参与外部评审而只做本地裁决与合成。
- 假设所有安全底线（密钥不落盘、不打印、真实调用显式开启）通过种子包和派生输入即可确保，而不依赖运行时的强制执行机制。
- 假设如果任一模型输出为空/超时/schema不合格，不伪造意见并标记缺失来源就是充分的降级处理。

### API 版本计划
- 假设在现有 prompt-only 流程之外新增 API-runner 路径，不替代旧路径，双轨并存更安全且可回退。
- 假设 API 调用默认 dry-run，必须显式 `--execute` 才能真正发出请求，并认为这种简单的布尔开关即可防止误操作。
- 假设外部 API 调用（Qwen、DeepSeek）串行执行，能简化并发带来的日志、安全和失败恢复问题，且不影响效率。
- 假设人工门禁仅在高风险未消解时才触发，而风险判定完全依赖 DeepSeek 的输出，未考虑到模型可能漏报或评估偏差。
- 假设 cost/audit 记录只需脱敏摘要（不包含完整 request/response），则认为通过文档规范就能保证脱敏执行到位。

### Qwen 原始方案
- 假设当前任务是从代码工程角度设计一个“稳定健壮的 API 调用客户端”，而不仅仅是生成 API 评审流程。
- 假设重试、熔断、结构化日志、声明式配置等标准工程实践可以直接平移到本方案，且不存在跨模型调用的特殊复杂度。
- 假设通过 Mock 测试覆盖 200/400/500 和参数序列化即可验证方案正确性。
- 假设需要人工确认的高风险项（重试、合规、降级）可以通过文档列出，执行者自然会处理，未考虑流程阻断和强制确认机制。

## 最强部分
- 种子包结构设计清晰，职责分离明确。`model_assignments` 和 `adjudication_rules` 提供了具体的冲突解决和阻断规则，避免了模糊的“综合评审”。
- API 版本计划中的 data flow 和 mermaid 图将 dry-run 与 execute 的分歧、高风险的阻断路径表达得很直观，并且引入了人工门禁角色。
- 安全规则明确禁止通过命令行参数传递真实 header，要求在内存中设置，这是容易被忽略的工程细节。
- Qwen 方案提出的“声明式配置 + 函数式封装 + 结构化日志”架构模式确实能提高单一调用链路的健壮性和可维护性。
- Qwen 方案中关于重试策略需要人工确认的提醒（尤其涉及资金操作的接口禁止自动重试）是重要的业务边界思考。

## 检查维度

从以下维度审核三个方案的落地可行性、安全、审计及过度设计风险：
- 流程完整性与单点故障
- 安全约束是否可执行而非仅是文档声明
- 模型输出的依赖与信任边界
- 成本失控与滥用风险
- 人工门禁的强制性与可绕过性
- 过度工程与复杂性
- 可审计性

## P0/P1/P2/P3 问题

### P0（阻断落地，安全或业务严重风险）

1. **密钥安全仅靠文档约定，缺少运行时强制校验**
   - 三个方案都反复声明“不得打印密钥”“只能从环境变量读取”，但没有设计任何自动化检查机制。
   - 在实际 API 调用中，如果代码实现阶段未进行脱敏日志拦截，或调试打印了完整 response/request，密钥可能意外泄露。
   - 评审/计划阶段缺失这类技术防护设计，属于 P0 级安全缺陷。
   - 建议：必须在 API client 封装层或日志模块中实现强制脱敏，任何包含 `Authorization` 的 header 或 token 被替换为 `****`；对完整 response body 写入默认使用 truncate+scan，仅允许脱敏摘要写入长期存储。

2. **Dry-run 机制依赖单一变量，可能被绕过或误开**
   - API 版本计划中，dry-run 是默认值，`--execute` 显式开启。但一次脚本调用或变量覆盖即可意外执行真实 API 调用。
   - 没有二次确认（如交互式确认或需要 provide 另一个 token），容易在生产/CI 环境中因错误配置发起真实调用，造成成本或数据风险。
   - 人工门禁只针对“高风险未消解”，但低风险或未识别风险的调用仍会直接执行，而模型可能漏报风险。
   - 建议：在 `--execute` 模式下增加强制确认环节（如要求输入 `--confirm-execute` 且提供非默认环境标识符）；增加环境变量 `MULTI_REVIEW_API_CALLS=enabled` 作为第二道闸门，必须同时开启才可执行。

### P1（高影响，可导致流程失败或安全边界模糊）

3. **DeepSeek 高风险判定作为唯一自动化阻断点，存在信任偏差**
   - 方案的自动阻断完全依赖 DeepSeek 输出的风险标记，但 DeepSeek 作为外部模型，可能输出不稳定、漏报或格式异常。
   - 如果 DeepSeek 超时或输出为空，其意见会被标记缺失而不是视为高风险，这可能导致真正的高风险方案绕过阻断。
   - 建议：Codex 在合成时不能仅依赖 DeepSeek 的风险标签；需要内置一个最小静态风险检查规则表（如涉及生产配置、资金、密钥轮换、敏感数据等关键词），无论模型输出如何，这些类型步骤强制标记为需人工确认。

4. **API 调用失败降级策略过于简单，可能导致流程静默失败**
   - 计划中 400/401/403 不重试、429 指数退避最多 2 次、5xx 最多 2 次。超时时不合成。但未明确超时后是否回退到 dry-run 或依赖人工，还是直接终止。
   - 如果恰好其中一个模型多次超时，整个规划阶段会卡住，没有一个明确的 fallback 路径（比如使用 prompt-only 替代或人工补充）。
   - 缺乏降级决策流程图，建议增加明确的“外部模型多次不可用时的回退机制”（使用不依赖该外部模型的本地静态流程，或进入人工接管）。

5. **成本记录未量化约束，可能导致费用超支**
   - 成本记录仅定义字段格式，但没有设置单次调用、每日或每任务的 token 上限或费用硬限制。
   - 如果方案被循环调用或 prompt 过长，可能产生不可控费用，且事后审计才发现。
   - Qwen 模型和 DeepSeek reasoning 模式本身费用较高，必须在发起调用前评估 prompt 长度，并在代码层面设置上限，超限则报错或要求人工审批。
   - 建议：在环境变量中增加 `MAX_API_CALL_COST_PER_TASK` 和 `MAX_DAILY_COST`，以及预检 prompt token 数的步骤；超出时立即中断并报告。

### P2（中影响，可维护性、完整性、效率问题）

6. **种子包派生输入与模型实际接收输入之间的验证缺失**
   - 计划称“Qwen/DeepSeek 输入从同一份种子包派生”，但未定义如何验证最终发送的 API 请求确实符合种子包 schema。
   - 如果派生时出现脚本错误（如遗漏字段、拼接错误），模型接收到的可能是不完整或错误的指令，导致输出不可用，而 Codex 在合成前难以发现输入侧的问题。
   - 建议：在 Codex 发出请求前，增加一个自动校验步骤，对比实际发送的 message 与种子包中 `review_inputs` 的结构是否一致，如不一致则中断并告警。

7. **Qwen 原始方案与评审流程匹配度低，可能造成目标偏移**
   - Qwen 方案更偏向于“如何写一个健壮的通用 HTTP 客户端”，而不是“如何编排多 AI API 评审流程”。
   - 它没有回答最小流程、API runner 架构、输入输出结构定义、错误处理与成本记录如何在多模型协作中落地。
   - 如果将其直接作为 API-runner 方案使用，将缺少多模型交互的关键部分。
   - 建议：Qwen 方案需要重新生成，聚焦于评审流程本身：状态管理、模型调用序列、结果校验、裁决逻辑、与 Codex 的接口协议，而不是通用 HTTP 客户端的实现细节。

8. **代码与配置分离的理想假设未考虑本任务的简化边界**
   - Qwen 方案提出声明式配置、客户端工厂模式、强类型定义等，在长期项目中合理，但当前任务是设计“基于 API 的评审方案”，可能只需一个脚本或简单 runner，过度工程会增加维护负担和错误面。
   - 当前阶段更适合“最小可行脚本”，过度封装可能导致种子包和裁决逻辑与具体 HTTP 调用耦合，反而降低灵活性。
   - 建议：先实现功能正确的最小集成（一个 Codex 脚本调度两次 API 调用并裁决），再根据实际痛点逐步引入封装。

### P3（低影响，文档、命名、体验优化）

9. **命令接口设计缺少帮助和预检模式**
   - `multi-review api-plan --dry-run` 只展示将调用的模型和输入来源，但没有预估 token 数和费用，不足以让用户判断是否值得开启 `--execute`。
   - 建议：在 dry-run 输出中增加估计 token 计数和预估成本（上限），提升决策质量。

10. **环境变量命名不一致且暴露敏感配置给进程树**
    - `QWEN_MODEL="qwen3.6-plus"` 和 `DEEPSEEK_MODEL="deepseek-v4-pro"` 可以作为默认值，但不应作为固定的环境变量名称要求，因为未来模型切换需改环境变量。
    - 建议使用 `MULTI_REVIEW_API_MODEL_QWEN` / `MULTI_REVIEW_API_MODEL_DEEPSEEK`，并允许通过任务参数覆盖，避免多个任务共用全局变量时冲突。

11. **测试计划中缺乏异常注入和 chaos 测试**
    - 测试虽包含 dry-run、最小 OK prompt、安全测试，但没有模拟网络超时、429/500 重试行为、部分响应格式异常等真实世界问题。
    - 建议增加“遥测测试”：使用 Mock 服务注入延迟、错误响应、非 JSON 返回，验证降级行为是否符合设计。

## 建议采纳、拒绝或修改的点

### 强烈建议采纳
- 种子包结构作为统一上下文来源，保持对外部模型输入的一致性和可追溯性。**采纳。**
- 安全底线（密钥不落盘、不打印、显式 `--execute`）作为硬约束贯穿所有环节。**采纳，但必须补上运行时强制技术措施。**
- 明确 Codex 为本地集成与裁决者，不参与外部评审；Qwen 与 DeepSeek 角色固化。**采纳。**
- 脱离交叉评审默认，仅高风险或争议时追加。**采纳。**
- 成本审计记录脱敏摘要格式。**采纳，但增加 token 使用上限和预检步骤。**

### 建议修改后采纳
- API-runner 流程中的 dry-run/execute 机制：**增加二次确认和闸门环境变量，防止误执行。**
- 高风险阻断逻辑：**不能只依赖 DeepSeek 输出，Codex 内置静态特征风险检查，两者结合触发阻断。**
- 失败降级路径：**增加单一模型多次失败的 fallback 方案，明确何时回退到 prompt-only 或人工接管。**
- Qwen 方案需重定向焦点：**要求其输出多模型评审流程的编排设计，而不是通用 HTTP 客户端最佳实践。**
- 种子包到外部模型请求的校验：**增加发送前 schema 合规校验步骤，防止指令变形。**

### 建议拒绝
- Qwen 方案中“声明式配置 + 客户端工厂 + 强类型定义”作为当前第一轮输出的主要建议：**拒绝在现阶段采用，属于过度设计；先实现最小可行评审 runner。**
- 仅依靠文档约定保障安全的假设：**拒绝接受，必须在架构设计中体现强制脱敏和访问控制。**

整体评价：三个被评内容已经将多 AI API 评审的框架和分工界定得比较清晰，但在安全执行、风险阻断的可靠性、成本失控防护、降级策略等关键工程点仍停留在“约定优于实现”的层面。补充这些薄弱点后，方案即可具备较强的落地性。
