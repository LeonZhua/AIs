## 目标理解

本任务旨在为“直接调用 API 接口”的系统或功能设计一套多 AI 评审方案。所谓“直接调用”，通常指代码中硬编码 API 端点、密钥、请求参数，跳过中间封装或网关层。需要评审的内容可能包括：接口契约（请求/响应结构）、错误处理、重试/超时策略、安全风险（密钥泄露、注入、未授权访问）、成本控制（API 计费模式）、以及可观测性（日志、监控、链路追踪）。反方视角要求我们识别该评审方案自身可能引入的漏洞、边界条件、过度设计以及隐藏成本，而不是无脑接受“多 AI 评审一定更好”的假设。

## 关键约束

1. **评审范围必须明确**：避免将“直接调用 API”与“通过 SDK/封装库调用”混淆。评审应聚焦于原始 HTTP 调用、无中间抽象层、无统一认证网关的场景。
2. **成本敏感**：多 AI 评审（尤其是 `full` 模式）会消耗大量 token 和人工时间。若 API 调用本身极低频或低风险（如内部工具只调用一次），评审成本可能超过收益。
3. **无自动执行分派**：v1 协议规定不自动调用 API、不保存 API Key、不自动执行分派。因此评审产出只能提供建议，不能强制代码变更或运行时拦截。
4. **人工确认门槛**：P0/P1 问题必须人工确认。若评审方案要求人工确认项过多，会导致流程阻塞，实际效率可能低于单人审查。
5. **模型偏见与隔离**：独立方案阶段禁止模型间互通，但评审模型仍需复述被评方案核心假设。当被评方案本身就包含错误假设时，复述行为可能放大错误而不易察觉。
6. **验收标准可执行性**：所有验收标准必须能用脚本或人工检查验证，避免“设计良好”“架构优雅”等模糊指标。

## 推荐方案（反方视角：优先简化，避免过度依赖多 AI）

与其设计一个全量 `full` 模式的多 AI 评审，不如采用以下 **分级 + 单 AI 复核** 策略，只在必要时引入第二个模型。具体步骤：

1. **分类 API 调用风险等级**
   - 低风险（内部只读、调用量 ≤100 次/天、无资金/安全影响） → 无需多 AI 评审，仅人工快速过一遍即可。
   - 中风险（读写混合、影响业务但非关键、调用量可控） → Codex 生成单份评审报告，再由 DeepSeek 做一次低成本反向审查（使用 `light` 模式）。
   - 高风险（支付、鉴权、数据删除、生产配置、大额计费） → 使用 `full` 模式，但限定最多 2 个外部模型（例如 DeepSeek + GLM），避免 Kimi 和 Qwen 同时上阵导致决策噪音。

2. **协议简化：去掉不必要的 artifact**
   - 当前协议要求 `plan_prompts` → `plans_waiting` → `plans_ready` → `reviews_waiting` → `reviews_ready` → `adjudicated` → `human_decisions_ready` → `final_plan_ready` 等 10+ 状态。对于大多数 API 调用评审，可以合并为：生成草案 → 交叉评审 → 裁决（人工 or 自动） → 最终计划。状态机过度设计会浪费维护成本。

3. **引入“运行时自检”而非纯静态评审**
   - 直接调用 API 的许多问题（超时、限流、脏数据）只能在运行时发现。评审方案应要求设计一段测试代码（例如 `curl` 脚本或单元测试）实际调用 API 沙箱环境，并将结果作为评审输入的一部分。这比多模型纸上谈兵更有效。

4. **为评审方案自身设置边界条件**
   - 当 API 文档错误或缺失时，多 AI 评审可能基于相同错误假设给出一致但错误的建议。此时需要强制人工补充文档或抓包验证。
   - 当 API 返回非 JSON（如 XML、纯文本、二进制）时，评审模型可能无法正确解析，应提前声明“仅评审 JSON API，其他格式需人工处理”。

5. **成本控制具体措施**
   - 限制每个模型输出长度 ≤2048 token，避免高额 token 费用。
   - 使用本地小模型（如 Llama 3 8B）做第一轮过滤，只有触发规则才调用云端大模型。
   - 如果 API 调用量极小（<10 次/天），直接拒绝执行任何多 AI 评审，改为人工 checklist。

## 执行步骤

1. **输入准备**：收集 API 规范（OpenAPI 文档或人工描述）、调用代码片段、实际请求/响应示例、历史故障记录（如有）。
2. **风险分级**：根据上述分类标准标记等级（低/中/高）。若为低，直接跳至步骤 9。
3. **（仅中/高）生成单份评审草案**：由 Codex 或人工编写初始评审报告，包含：端点正确性、认证方式、参数校验、错误码处理、超时/重试配置、幂等性设计。
4. **（仅高）引入一个外部反方模型**：将草案和原始 API 规范提供给 DeepSeek，要求其只指出漏洞和遗漏（采用 `light` 模式，不生成完整 plan）。
5. **（仅高且争议项 ≥3）**：才引入第二个模型（GLM）做仲裁。避免两个模型给出类似意见导致浪费。
6. **运行时验证**：编写一个临时测试脚本（Python 或 curl），在沙箱环境（如测试 API key、mock server 或 staging 环境）执行至少 3 种场景：正常请求、边界参数、错误触发（如无效 token）。
7. **人工确认关键项**：将以下内容整理为 `human-decisions.md` 列表：
   - 是否允许使用硬编码密钥（建议不允许）；
   - 是否接受 5xx 重试 3 次（取决于 API 提供方 SLA）；
   - 是否记录全量请求/响应（可能涉及数据合规）。
8. **生成 final plan**：明确写出代码需修改的具体位置、配置项、新增的错误处理逻辑、监控指标（如 `api_call_duration`、`api_error_total`）。
9. **（若低风险）输出人工 checklist**：5 项以内的问题，要求开发者在 PR 中自检并勾选。

## 验收标准

- [ ] **风险分级结果**已记录在 task.md 中，且有明确依据（如“调用涉及删除用户数据，故为高风险”）。
- [ ] 对于中高风险，至少执行一次运行时测试脚本，且脚本输出日志保存至 `test_output/`。
- [ ] 如果使用了多 AI 评审，每个模型的输出时间戳与 token 近似消耗已记录（便于后续成本核算）。
- [ ] 最终计划中不含模板占位符（如 `[TODO]`）。
- [ ] 所有 P0 项（如密钥明文、无超时设置）均已被标记为“必须修改”，且有人工确认签字（或 issue 链接）。
- [ ] 验收时执行一次模拟调用（可使用 `--dry-run` 模式），确认代码按计划行为运行。

## 风险与边界

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 多 AI 评审产生互斥建议（如一个要求指数退避重试，另一个要求快速失败） | 决策僵局，人工介入成本高 | 提前约定裁决规则：以 API 提供方官方建议为准，若无则采用更保守（重试少）的方案 |
| 评审方案自身过度设计，导致评审时间 > 修复时间 | 浪费团队产能 | 设置时间上限：低风险 ≤ 15 分钟，中风险 ≤ 1 小时，高风险 ≤ 3 小时。超时则强制人工决策 |
| API 文档与实际行为不符 | 评审基于错误前提，输出无效建议 | 强制要求运行时验证脚本优先于模型评审。若实际行为与文档差异大，需暂停评审并更新文档 |
| 直接调用 API 导致密钥泄露（如前端打包泄露） | 安全事故 | 评审必须提出：禁止在前端直接调用，必须通过后端代理；如确需前端调用，必须使用临时令牌和 CORS 限制 |
| 模型幻觉（编造 API 参数或错误码） | 引入错误修改 | 所有模型建议必须附带引用来源（官方文档章节、实际返回示例），否则视作无效并丢弃 |
| 成本失控（调用 100 次 GPT-4 评审一个日调用 10 次的 API） | 浪费 | 在 final plan 中增加成本评估表：预估 API 调用月成本 vs 评审成本。若评审成本 > API 成本 ×10，则不应执行 full 模式 |

## 需要人工确认的问题

1. **是否允许评审方案自动修改代码？**  
   - 当前协议 v1 禁止自动执行分派，但未明确禁止生成可直接应用的 patch。建议人工确认：仅输出建议，或者可生成 PR 但需人工 review 后合并。

2. **当 API 提供方变更接口（如弃用旧版本）时，评审方案是否要求重新评审？**  
   - 建议人工确认策略：只有涉及安全或破坏性变更才重新 full 评审；兼容性变更仅更新文档。

3. **是否接受模型评审出“无问题”但实际运行时出错的后果归责？**  
   - 需明确声明：模型评审仅为辅助，最终责任由代码提交者承担。团队需签字认可这一原则。

4. **对于超高频 API（>1000 次/秒），多 AI 评审是否需要额外考虑性能测试？**  
   - 人工确认：是否将性能测试作为评审的一部分（例如要求提供压测报告），还是认为超出范围。

5. **评审方案本身是否需要一个“评审评审”来防止过度设计？**  
   - 建议人工确认：每个 quarter 对多 AI 评审流程进行一次复盘，若发现实际收益低于预期，则降级为人工+单模型。
